# ADR: владелец заявок и разграничение доступа

## Контекст

В первой версии таблица заявок не связывала каждую заявку с пользователем. Это было достаточно для ручного сбора заявок, но не позволяло различать, кому принадлежит запись и кто имеет право её просматривать.

Во второй версии появилось два типа доступа:

- родитель должен видеть только свои заявки;
- сотрудник «Рядом» должен видеть все входящие заявки.

## Решение

В таблицу заявок добавляется ссылка на идентификатор пользователя-владельца. Авторизация реализуется только библиотекой Better Auth по электронной почте и паролю; идентификаторы сессий, пароли и таблицы сессий библиотека создает и хранит сама.

API перед выдачей списка заявок получает серверную сессию Better Auth. Для роли `parent` запрос фильтруется по идентификатору владельца. Для роли `staff` выдаются все заявки. Без авторизованной сессии список заявок недоступен.

## Почему общего списка заявок недостаточно

Общая таблица без владельца:

- не позволяет однозначно определить связь заявки с родителем;
- не предоставляет серверную основу для фильтрации данных родителя;
- может раскрыть заявки другого родителя при ошибке клиентской проверки;
- не отделяет доступ сотрудника от доступа родителя.

Ссылка на владельца переносит проверку доступа на серверный уровень. Отправка формы требует сессии родителя; API не сохраняет анонимные заявки и не позволяет сотруднику создавать записи.

## ADR: отправка заявки с владельцем (версия 2, уточнение текущей версии)

**Решение:** Новую заявку может создать только авторизованный пользователь с ролью `parent`; `owner_id` берётся из серверной сессии, а клиентская регистрация не может назначить роль `staff`.

**Когда принято:** Базовая связь заявки с владельцем добавлена в версии 2. Требование обязательной сессии для отправки уточнено после версии 3 и реализовано в текущем коде.

**Какое требование изменилось:** В исходной версии 3 заявка могла отправляться без входа. Теперь каждая новая заявка должна принадлежать вошедшему родителю.

**Почему прежнее решение перестало подходить:** На исходном коммите версии 3 (`8a15ec0`) корректная анонимная отправка возвращала `201` и сохраняла заявку с `owner_id = NULL`. Такую запись не видел ни один родитель, а контактные данные оказывались вне связи с аккаунтом.

**Что сделали вместо этого:** В Better Auth отключён клиентский ввод `role`; seed назначает роль сотрудника серверным SQL-обновлением. `POST /api/applications` проверяет сессию и роль `parent` до валидации и записи, а браузер при `401` переводит пользователя на `/login.html`.

**Какой сценарий проверили после изменения:**

1. На исходном коммите `8a15ec0` отправили корректную заявку без сессии: API вернул `201`, запись появилась с пустым `owner_id`.
2. В текущей версии отправили ту же заявку без сессии: API вернул `401`, число записей не изменилось, форма перенаправила на вход.
3. После входа родителя отправили заявку повторно: API вернул `201`, `owner_id` совпал с ID родителя в сессии, заявка появилась в его списке.
4. Signup с переданным `role: staff` создал пользователя с ролью `parent`; учебные записи `parent@ryadom.local` и `team@ryadom.local` вошли с ролями `parent` и `staff`. Сотрудник увидел заявку в общем списке.

## Альтернативы

Собственная таблица пользователей, собственное хеширование паролей, собственные токены и собственная таблица сессий не используются — это противоречит выбранному техническому контуру с Better Auth.

## ADR: разделение слоёв приложения (версия 3)

### Ситуация до

`server.js` содержал запуск Express, настройку таблицы заявок и миграцию владельца, SQL-операции, валидацию и обработчики API, а также подключение статической папки. Представление уже хранилось отдельно: страницы и браузерные скрипты находятся в `public/`.

### Проблема

Смешение операций с БД и HTTP-обработчиков затрудняло независимое изменение и проверку логики заявок. При изменении API возрастал риск затронуть запросы к хранилищу. Разделение ответственности упрощает дальнейшую разработку без изменения поведения приложения.

### Решение

- `storage/applications.js` отвечает за создание таблицы, совместимость схемы и чтение/запись заявок.
- `api/applications.js` содержит валидацию, маршруты и проверки Better Auth/ролей.
- `presentation/static.js` подключает существующие представления из `public/`.
- `server.js` остаётся точкой композиции и запуска приложения.

Новые зависимости не добавлялись; механизм авторизации и пользовательский интерфейс не менялись.

### Проверенный сценарий

На исходном коммите версии 3 (`8a15ec0`) на одном запуске сервера без перезапуска между сценариями проверены:

1. Авторизованный родитель отправил заявку с лендинга и увидел её в списке «Мои заявки».
2. Родитель открыл список и получил только принадлежащие ему заявки.
3. Сотрудник вошёл после выхода родителя и увидел все заявки, включая только что созданную.
4. Отправка заявки без авторизации вернула успешный ответ; просмотр списка без авторизации вернул `401`. Это историческое поведение V3; в текущей версии анонимная отправка отклоняется согласно ADR выше.
