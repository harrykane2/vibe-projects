# План разработки лендинга «Рядом»

План соответствует первой версии: лендинг и ручной подбор нескольких вариантов занятий для родителя.

## 1. Зафиксировать MVP-документы

Подтвердить цель продукта, целевую аудиторию, основной сценарий, поля заявки и точные текстовые placeholders по [spec.md](spec.md).

**Проверка завершения:**

- В [spec.md](spec.md) указана аудитория родителей с детьми 4–12 лет.
- Заголовок «Сравним кружки за вас — по цене и дороге», поля и подтверждение сохранены согласованно.
- Нет перечисленных в MVP функций мобильного приложения, полного каталога, личного кабинета и онлайн-оплаты.

## 2. Согласовать правила ручного сбора данных

До сбора секций команда фиксирует единые правила для названия, стоимости за месяц, дополнительных платежей, возраста, расписания, адреса и времени в пути.

**Проверка завершения:**

- Существует единый бланк или таблица для каждой секции.
- Каждая запись содержит проверяемые поля и источник сведений.
- Правила для полной стоимости и дополнительных платежей согласованы до сбора данных.

## 3. Собрать начальный набор секций

Собрать несколько реальных секций по согласованным правилам. Порядок запуску ещё не определяет конкретные города или категории — они выбираются по собранным данным.

**Проверка завершения:**

- Для каждой секции указаны название, цена за месяц, дополнительные платежи, возраст, расписание, адрес и доступное для проверки время в пути.
- Все сведения сверены с первоисточником на момент проверки.
- Набор содержит несколько вариантов, а не полный каталог города.

## 4. Подготовить тексты первого экрана

Зафиксировать согласованные заголовок, подзаголовок и кнопку заявки для лендинга. Структура текста не должна выходить за возможности ручного подбора.

**Проверка завершения:**

- На первом экране показывается заголовок «Сравним кружки за вас — по цене и дороге».
- Кнопка ведёт к форме заявки.
- Текст не обещает автоматический поиск, полный каталог, интерактивную карту или онлайн-оплату.

## 5. Подготовить макет первого экрана

Создать макет лендинга на основе согласованного текста и собранных секций. Если карточка секции используется в макете, цена должна находиться на видном месте, а сведения о дороге оставаться доступными в деталях.

**Проверка завершения:**

- Карточка секции содержит название, стоимость за месяц, возраст и отзыв только в том случае, если эти сведения подтверждены исходными материалами.
- Первый экран ведёт к форме заявкой через кнопку.
- Макет не содержит личного кабинета, каталога всего города и оплаты.

## 6. Реализовать лендинг и форму заявки

Добавить HTML, CSS и JavaScript только после завершения документации и макета. Реализовать первый экран, форму и отображение ответа родителю.

**Проверка завершения:**

- Страница открывается локально и не падает при загрузке.
- Кнопка заявки открывает или прокручивает к форме.
- Форма отображает возраст ребёнка, район или школу, удобное время и способ связи.
- После отправки родитель видит подтверждение отправки.
- Нет мобильного приложения, личного кабинета, каталога всего города и онлайн-оплаты.

## 7. Настроить приём и учёт заявок

Определить, куда сохраняются заявки и как команда фиксирует ответ, исход подбора и причину отказа или выбора секции.

**Проверка завершения:**

- Тестовая заявка попадает в выбранное место хранения.
- Для заявки видны отправитель, согласованные поля и статус обработки.
- Команда может зафиксировать, была ли получена секция выбрана родителем.

## 8. Провести локальный сценарий

Запустить лендинг и вручную пройти основной сценарий от открытия страницы до ответа родителю.

**Проверка завершения:**

- Лендинг открывается по локальному адресу.
- Родитель видит заголовок «Сравним кружки за вас — по цене и дороге».
- Форма заполняется и отправляется без технических ошибок.
- После отправки выводится подтверждение отправки.
- Заявка сохраняется для ручной обработки.

## 9. Провести пять пробных ручных подборов

Проверить процесс на пяти тестовых заявках. Для каждого ответа сверить район отправления после работы, возраст ребёнка, расписание, адрес, полную стоимость и дополнительные платежи.

**Проверка завершения:**

- Подготовлено пять записей с заявкой, подобранными секциями и ответом родителю.
- В ответе указана стоимость с дополнительными платежами.
- Варианты проверены на соответствие доступному району, возрасту и расписанию.
- Зафиксированы исходы без добавления не реализованных функций.

## 10. Собрать метрики MVP

После запуска оценить долю посетителей с заявкой, долю заявок с выбранной секцией, долю положительных исходов после полного ответа о цене и заполняемость опционального поля о способе поиска.

**Проверка завершения:**

- Таблица или журнал содержит число открытий лендинга и число отправленных заявок.
- За каждую заявку есть статус обработки и исход по подбору.
- Заполняемость опционального поля о способе поиска считается отдельно.
- Метрики не используются как доказательство до получения реальных данных.

## 11. Зафиксировать решение по следующему этапу

По собранным метрикам команда принимает решение продолжить, изменить подход или остановить первую проверку. Решение относится к реальной обратной связи и не расширяет MVP автоматически.

**Проверка завершения:**

- Есть запись с фактическими метриками запуска.
- Решение отдельно поясняет, что меняется в первом экране и процессе подбора.
- Новые функции не добавляются без отдельного согласования и обновления спецификации.

## Вторая версия: вход и владельцы заявок

1. Подключить Better Auth для входа по электронной почте и паролю.
2. Создать cookie-сессии средствами Better Auth и необходимые таблицы библиотеки средствами её миграций.
3. Добавить роли `parent` и `staff` учебным учётным записям.
4. Связать заявки с идентификатором пользователя-владельца.
5. Добавить страницу входа и страницы просмотра заявок для каждой роли.
6. Ограничить API списков заявок на сервере по сессии и роли.
7. Проверить отправку заявки анонимным пользователем и владельцем родителем.

**Проверка завершения второй версии:**

- Вход родителя и сотрудника проходит по паролю через Better Auth.
- Пароли не хранятся в открытом виде.
- Родитель получает только заявки, у которых его идентификатор указан как владелец.
- Сотрудник получает все заявки.
- Запросы к списку заявок без cookie-сессии возвращают отказ.
- Отправка заявки с лендинга продолжает работать.
